# Retoucher cette image : spécification d'implémentation

Validé par JF le 2026-10-09. Raison d'être : « Faire une variante » recrée toute l'image à partir du texte, donc change aussi le décor et la prise de vue. La retouche envoie l'image existante à BFL avec une consigne de changement : le reste de l'image doit rester identique.

Essai réel du 2026-10-09 (chat roux en aquarelle, consigne « change la fourrure en blanc à rayures gris clair, garde tout le reste identique ») : fenêtre, arbres, cadrage, angle, style, position du chat et signature conservés ; seule la fourrure a changé ; mur et rideaux légèrement éclaircis. Un seul essai, aucune garantie de BFL sur la conservation de la composition. Coût annoncé par BFL dans la réponse : `cost: 4.5` (unité non précisée).

## API BFL (vérifié par un essai réel)
- `POST {baseUrl}/v1/{model}` (même chemin que la création), en-têtes identiques, corps `{ "prompt": "...", "input_image": "<URL https>" }`. Pas de `width`/`height` (la taille suit l'image d'origine), pas de `seed` (non documenté pour la retouche).
- Réponse identique à la création : `id`, `polling_url` (domaine `*.bfl.ai`), éventuellement `cost`. Le suivi (`poll`) et le téléchargement (`download`) sont inchangés.
- L'image d'origine est fournie par un lien signé de 300 secondes vers le bucket privé `img-generations`.

## Base de données
Fichier `supabase/migrations/20261009_imagactif_retouche.sql` (idempotent, à exécuter par JF dans le SQL Editor AVANT le déploiement) :
```sql
alter table img_generations add column if not exists edit_instruction text;
```
Aucun nouveau droit à accorder (les droits `select` de `authenticated` couvrent la nouvelle colonne). Mettre à jour `tests/db.integration.mjs` : un cas qui vérifie qu'un compte peut lire `edit_instruction` de ses lignes via `select('*')` (déjà couvert par select('*') existant : ajouter seulement si utile ; ne pas lancer le test).

## Serveur
1. `api/_lib/providers/bfl.js` : ajouter `edit({ apiKey, prompt, inputImageUrl })` dans `createBfl` (même gestion d'erreurs HTTP et même garde sur `polling_url` que `submit`, y compris le cas 422 « Invalid API key format »). Refuser (ProviderError `provider_error`) une `inputImageUrl` qui n'est pas en `https:`. Corps envoyé : `{ prompt, input_image }` uniquement. Retourne `{ id, pollingUrl }`.
2. `api/_lib/repo.js` : `signedUrl(path, secondes)` (service role, `storage.from('img-generations').createSignedUrl`) ; `insertGeneration` accepte `edit_instruction` (colonne texte).
3. Nouveau handler `api/_lib/handlers/retoucher.js` (`createRetoucheHandler`) et enveloppe `api/retoucher.js`, sur le modèle de `generate.js` (mêmes dépendances injectées : `requireUser, repo, bfl, dechiffrer, ring, env, now`), route `POST /api/retoucher`, corps `{ sourceId, instruction }` :
   - mêmes contrôles que `generate` dans le même ordre : méthode, session, e-mail confirmé, règles acceptées (`TERMS_VERSION`), régime (`determineRegime`, `trial_over` si `none`), génération des échecs périmés (+ remboursements), quota d'essai (`reserveQuota`, remboursé en cas d'échec), clé (`cleApi`), une seule génération en cours (`busy` -> 409 + remboursement) ;
   - `sourceId` : UUID valide (réutiliser `api/_lib/uuid.js`), sinon 400 `invalid_parent` ; la génération source doit appartenir à l'utilisateur, avoir `status = 'done'` ET `image_path` non nul, sinon 400 avec le code `source_indisponible` (message : « Cette image n'est plus disponible (elle est supprimée au bout de 30 jours) : faites plutôt une variante ou refaites une image. ») ;
   - `instruction` : chaîne, `trim`, de 3 à 500 caractères, sinon 400 `invalid_json` avec message clair (« Décrivez ce que vous voulez changer (3 à 500 caractères). ») ;
   - prompt envoyé à BFL = `${instruction}. Keep everything else exactly identical: the composition, the framing, the camera angle, the background, the lighting, the style and the colors.` (la partie anglaise est une constante exportée, testée) ;
   - lien signé : `repo.signedUrl(source.image_path, 300)` ;
   - ligne insérée : `user_id`, `json` = JSON de la source passé par `normaliserGabarit` puis augmenté d'une entrée `personnalise` `{ nom: 'Retouche', valeur: instruction }` si `personnalise` compte moins de 10 entrées (sinon JSON inchangé), `prompt_text` = prompt complet envoyé, `seed` = seed de la source, `model` = `bfl.model`, `key_mode`, `quota_day`, `parent_id` = source, `edit_instruction` = instruction ;
   - appel `bfl.edit(...)` puis `repo.insertJob` ; réponse 202 `{ id }` ; en cas d'échec fournisseur : `markFailed`, remboursement, même table de statuts que `generate` ;
   - `status.js` n'a pas besoin de changer (il suit, télécharge, stocke ; vérifier qu'il fonctionne avec une génération retouchée, la clé utilisée étant celle du `key_mode` de la ligne).
4. `src/lib/messages.js` : ajouter `source_indisponible`.
5. Tests (vitest, mêmes helpers que generate.test.js ; adapter `tests/helpers.js` : `fakeRepo.signedUrl` renvoie `https://signed.example/x` et `fakeBfl.edit`) : un fichier `retoucher.test.js` couvrant 405, 401, e-mail non confirmé, règles non acceptées, `trial_over`, instruction vide/trop courte/trop longue, `sourceId` non UUID, source introuvable ou d'un autre utilisateur, source sans image (supprimée) ou non terminée, essai (quota réservé, clé de JF, lien signé de 300 s demandé pour le bon chemin, `bfl.edit` appelé avec la bonne URL et le prompt attendu, ligne insérée avec parent, edit_instruction et JSON augmenté), clé personnelle (pas de quota), `busy` (409 + remboursement), échec BFL (marqué échoué + remboursement), JSON déjà à 10 entrées `personnalise` (inchangé). Tests de `bfl.edit` dans `bfl.test.js`.
